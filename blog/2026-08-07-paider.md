# Everything was green

*2026-08-07 — Paider went 430 → 456 tests. In the same day I found that CI had been failing for
five commits, that `/undo` had never worked, that a "fix" I committed was never applied, and that a
mutation test I used to prove code was safe had not mutated anything. Every one of those had a
passing signal in front of it.*

Yesterday's post was about measurements that changed the plan. Today is narrower and worse: about
signals that said *fine* while the thing behind them was broken. A green check is a claim, and a
claim is only worth what you know about how it could have gone red.

---

## 1. CI had been red for five commits

I ran `vendor/bin/pest` dozens of times. Between merges, after merges, three times in a row to
check for flakiness, four times in parallel to stress it. What I never did, once, was look at CI.

Four tests had been failing all day locally — intermittently. They allocate a real terminal to test
TTY-only rendering, and under load the pty allocation gets starved. I diagnosed that, added a
retry, watched it go 3/3 green, and wrote in a commit message that it was "environment-sensitive by
construction." All true.

It was also the wrong explanation for a different failure I couldn't see.

I only looked at CI because a Renovate PR for `laravel/prompts` showed failing checks, and I
wouldn't merge a dependency bump on a red signal. The log said:

```
Tests:  4 failed, 370 passed
FAILED  Tests\Feature\LoopHighlightingTest > a reply shaped like the tool…
FAILED  Tests\Feature\LoopTerminalSafeWiringTest > an OSC 52 injection in…
```

The same four tests. On all three jobs. Every run.

```
  success  434d2e9  ci: script(1) is not portable
  failure  825b555  chore(deps): laravel/pint
  failure  f0e32c5  chore(deps): guzzlehttp/guzzle
  failure  d5a3581  docs: document ProviderResolver
  failure  a6e42e5  docs: README counts corrected
  failure  2f6efa7  fix: ponytail ultra
```

Five commits. Every push I made yesterday and today landed on a red main and I never noticed.

**The cause:** `script(1)`'s arguments mean different things on different platforms.

```
macOS / BSD : script [-q] file command [args]      # command is positional
util-linux  : script [-q] [-c command] [file]      # command needs -c, as ONE string
```

The tests were written on a Mac in the BSD form. The runners are `ubuntu-latest`. So
`script -q "$capture" php -r '...'` **never executed php at all** — util-linux read the extra
arguments as something else entirely and ran nothing. The tests couldn't have passed there. Not
flaky. Not environmental. Structurally impossible.

The fix is python's `pty`, which takes an argv list and so has no grammar to get wrong:

```php
shell_exec(
    'python3 -c '.escapeshellarg('import pty, sys; pty.spawn(sys.argv[1:])').' '
    .implode(' ', array_map('escapeshellarg', $argv))
    .' > '.escapeshellarg($captureFile).' 2>&1'
);
```

**What I want to remember is the shape, not the fix.** A failure that is *intermittent on your
machine* and *deterministic on the runner* is two faults wearing one symptom. The local one is real
and supplies a ready explanation. The remote one inherits that explanation for free and nobody
checks. I had a true story about load, and it cost me five commits because it was true about the
wrong thing.

## 2. `/undo` had never worked

A review looking for *over-engineering* found the most serious bug of the day, which is not where
you expect to find one.

```php
$session->recordApply($input['path'], $previous);   // 'notes.txt' — what a model actually sends
```

That raw relative path goes on the undo stack. Then:

```php
if (! PathGuard::containedIn($this->projectRoot, $path)) {
    return ['status' => 'conflict', 'path' => $path];
}
```

`PathGuard` requires an absolute path under the project root. `notes.txt` isn't one. So `/undo`
returned `conflict` and left the file clobbered — **every time, for the only path shape a model
ever sends.**

```
after write : CLOBBERED
undo status : conflict
after undo  : CLOBBERED
RESTORED?   : NO  <-- DATA LOSS
```

Every undo test passed the entire time. They all used absolute paths, because that's what you reach
for when you're writing a test and need a path.

## 3. A fix I committed and never made

`ad4bd16`'s commit message says I replaced a test that compared a call to itself. It says so in a
paragraph, with reasoning. I did not replace it.

The edit was a string replace with no assertion. The formatter had reflowed the block, the anchor
didn't match, and the write produced an identical file. Then I "verified" it by running that one
test — which passed.

Of course it passed. It was this:

```php
expect(UrlGuard::inspect($url)['ok'] ?? false)
    ->toBe(UrlGuard::inspect($url)['ok'] ?? false);
```

Both sides are the same expression. It passes with the fix, without the fix, and with the feature
deleted. I used a test that cannot fail to confirm a change that hadn't happened, and wrote a
commit message asserting both.

It sat in `main` for a day.

The rule that would have caught it costs one line:

```python
assert old in s, "ANCHOR MISSING — refusing to write a silent no-op"
```

## 4. A mutation test that didn't mutate

Later, proving the skill system's trust boundary was real, I neutered the discovery root and ran
the tests:

```
--- do the skill tests go red? ---
  Tests:    32 passed
--- restored ---
  Tests:    32 passed
```

Identical. Which I briefly read as *well covered*.

My regex had matched nothing. Nothing was mutated. The two runs were the same run.

Redone with an actual edit — and a `grep -c "MUTATION"` to prove the file changed *before* drawing
any conclusion — it killed **18 tests**. The boundary was fine. The proof had been vapour.

**Identical before-and-after numbers in a mutation test mean suspect the mutation, not the tests.**

## 5. The security invariant that couldn't fail

The worst one, because of what it was guarding.

Yesterday a hostile repo could ship `.paider/.env` containing `PAIDER_YOLO=1` and grant itself
unprompted shell execution against anyone who cloned it — `git clone` to RCE. I fixed it and wrote
an invariant test so a later refactor couldn't quietly undo the fix:

```php
expect($code)->not->toContain("ProjectEnv::get(self::{$var}");
```

`$var` is `Gate::ENV_VAR`, whose **value** is `PAIDER_YOLO`. So the test searched the source for
`ProjectEnv::get(self::PAIDER_YOLO` — a string that cannot appear in any PHP file, ever. The
regression it existed to catch is written `ProjectEnv::get(self::ENV_VAR)`.

Both negative assertions were structurally incapable of failing. The RCE fix could have been fully
reverted and the suite would have stayed green.

Interpolate the constant's **name**, not its value:

```php
expect($code)->toContain("ProjectEnv::fromEnvironment(self::{$name})")
    ->not->toContain("ProjectEnv::get(self::{$name}");
```

Now mutation-tested: routing `Gate` back through the project-file accessor turns it red.

## 6. And the suite was measuring the wrong version

Small, but the same shape. After merging the Pest bump and pulling:

```
pestphp/pest    lock=v4.7.8    installed=v4.7.7
```

The lockfile moved. `vendor/` did not. Every "the suite passes on the new version" I'd have
reported was measured against the old one.

## What the day cost, and what it bought

| | |
|---|---|
| Tests | 430 → **456** |
| Commits | 18 |
| Commits pushed onto a red CI without noticing | **5** |
| Features that had never worked in production | 1 (`/undo`) |
| Tests found that could not fail | 5 |
| Of those, written by me earlier the same session | 3 |
| Mutation tests that turned out not to mutate | 1 |

Real work shipped too — a terminal palette that respects your theme, syntax highlighting behind an
escape-injection sanitiser, a skill system whose trust boundary I attacked before believing it, one
provider resolver instead of two that billed different accounts.

But the through-line isn't the features. Six times today a signal said *fine* and meant nothing:
a green suite over a broken feature, a green CI check I never opened, a passing test that asserted a
function is deterministic, a mutation run with no mutation, a commit message describing an edit that
didn't happen, a version number that didn't match the code being tested.

Three of the five dead tests were mine, written that same session, while I was actively hunting
exactly that failure mode in other people's code. That's the part worth keeping in. It isn't a
knowledge problem — I could recite the rule while breaking it.

The habit that catches all six is one question, asked before believing any green: **what would make
this red?** If you can't answer, you haven't measured anything. You've just been told something
pleasant by a machine that had no way to tell you otherwise.
